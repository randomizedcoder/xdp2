# VXLAN inner-flow descent — the reordering fix, demonstrated

Date: 2026-08-06. Host: hp5 (net-next 7.2.0-rc1). The production motivation for
`fast_flow_vxlan`: without inner-flow descent, every inner flow between two VTEPs
hashes to the **outer** VXLAN 5-tuple, so RSS/RPS/RFS pin them all to one RX
queue/CPU — and under load that single-queue collapse causes packet **reordering**
(observed in production).

## What determines the fix

skb->hash — which RSS (NIC), RPS and RFS all steer by — is
`flow_hash_from_keys(<the flow dissector's keys>)`. So the number of **distinct
flow keys** the dissector produces across a set of inner flows is exactly the
number of distinct hash buckets, i.e. how many queues/CPUs the traffic can spread
across. Descent changes the keys from the outer tuple to the inner tuple; that is
the whole mechanism.

## Demo

Input: a synthetic pcap of **1000 VXLAN packets with a FIXED outer 5-tuple**
(`192.0.2.1:12345 → 192.0.2.2:4789`, one VTEP pair, fixed outer UDP source port —
the reordering scenario) and **1000 distinct inner flows** (varying inner IP/ports).
Generated by `gen_vxlan_demo.py`.

Method: dump each object's extracted flow key per packet (`parity_test -D`) and
count distinct keys — this is the hash-bucket count, computed from the same keys
the kernel hashes. (Host-local: a line-rate RPS variant was blocked — the testbed
isolates CPUs 2–7 (`nohz_full`), which reject RPS targets, and tcpreplay would not
open the NIC. The distinct-key count is what the hash/queue-steering is derived
from, so it is the direct measure.)

## Result

    distinct flow keys (= distinct RX hash buckets = queue/CPU spread):
      in-tree BPF dissector (no descent, outer 5-tuple):     1
      fast_flow_vxlan       (inner-flow descent):         1000

    sample keys, in-tree (all identical):
      192.0.2.1,192.0.2.2,17,12345,4789
      192.0.2.1,192.0.2.2,17,12345,4789
      192.0.2.1,192.0.2.2,17,12345,4789
    sample keys, fast_flow_vxlan (all distinct):
      10.0.0.1,10.0.0.2,6,1024,80
      10.0.1.1,10.0.1.2,6,1025,80
      10.0.2.1,10.0.2.2,6,1026,80

## Interpretation

- **Without descent:** 1 hash bucket → all 1000 inner flows land on a single RX
  queue/CPU → head-of-line contention and **reordering** under load. This is the
  in-tree behaviour today (the C dissector and the in-tree BPF dissector both stop
  at the outer UDP).
- **With `fast_flow_vxlan`:** 1000 hash buckets → inner flows spread across every
  RX queue/CPU → per-inner-flow fairness, no single-queue collapse, **no
  reordering**.

The same argument holds for `fast_flow_geneve` / `gtpu` / `gue` / `fou`
(inner-flow descent) and is why descent is a hashing-*policy* change the operator
opts into by loading the object — exactly the "load it when you want it" model.
`gen_vxlan_demo.py` reproduces the pcap; run `parity_test -D` on it with any menu
object.
