# Compiler comparison: clang-21 vs gcc-15 on c-xdp2-mono (Zen 1)

Date: 2026-05-20. Option B from `docs/perf-next-steps.md`:
test whether the 36 ns/pkt rust-mono tunnel gap is closable
by switching the C codegen backend from gcc to clang (i.e.,
to LLVM, the same backend rustc uses).

**Definitive result: clang is universally slower or equal to
gcc on every workload on hp5. The rust-mono tunnel advantage
is NOT explained by gcc-vs-LLVM backend choice.**

## Setup

- **gcc build**: `nix build .#flow-dissector-matrix-artifacts`
  (`pkgs.stdenv`, gcc 15.2.0, default flags).
- **clang build**: `nix build .#flow-dissector-matrix-artifacts-clang`
  (`pkgs.clangStdenv`, clang 21.1.8, same flags + `NIX_ENFORCE_NO_NATIVE=""`
  to allow -march=native).
- Both use identical compile flags: `-std=gnu11 -g -O3 -march=native -flto -fno-plt`.
- Both compile the same `parser.mono.c` (generated by xdp2-compiler,
  gcc-built either way — the codegen tool is unchanged).
- Same `benchmark.c` userspace harness.
- Same workload pcaps.
- Host: hp5 (Ryzen 5 PRO 2400G, Zen 1, DDR4 @ 1866 MT/s).
- Bench: `benchmark -p -n 200 <pcap>`, `XDP2 parser:` line
  (c-xdp2-mono via the post-R8 default).

## Per-workload c-xdp2-mono ns/pkt

| workload | gcc-15 | clang-21 | Δ (clang − gcc) |
|---|---:|---:|---:|
| https-web | 67 | 70 | +3 (small regression) |
| nfs-server | 65 | 65 | 0 |
| **pppoe-isp** | 66 | **105** | **+39 (large regression)** |
| vlan-tcp-mix | 64 | 70 | +6 (regression) |
| k8s-microservices | 124 | 126 | +2 (noise) |
| **vxlan-k8s-pure** | 125 | **129** | **+4 (regression, opposite of hypothesis)** |

Numbers above are from a single replicate per cell (taskset -c 3,
200 iterations × 19822 packets per impl). Smoke noise ±2-3 ns.
The pppoe-isp +39 ns and vlan-tcp-mix +6 ns deltas are well
outside the noise band.

## Why clang is slower

Not investigated in detail, but plausible reasons:

1. **gcc's `__builtin_expect` handling on switch statements**.
   R7-B1 added `if (__builtin_expect(type == HOT_VALUE, 1))
   goto label_HOT_TARGET;` before each per-node switch. gcc
   uses the hint to bias branch layout; clang may handle it
   differently.

2. **gcc's constant-folding through `static const` proto_def
   structs**. The mono parser relies on gcc seeing through
   `(const struct xdp2_parse_node *)&node` casts to constant-
   fold runtime field reads. clang may be more conservative
   on this folding pattern.

3. **PPPoE fast-path interaction**. The +39 ns pppoe-isp
   regression is dramatic. The PPPoE fast-path chain in
   `mono_def.template.c:R3.4.5d` does PPPoE+IPv4+TCP/ICMP
   inline extraction. clang may be making particularly bad
   inlining or layout decisions for the multi-level header-
   strip pattern.

4. **`-flto` driver differences**. gcc's LTO and clang's
   ThinLTO have different inlining heuristics. Same `-flto`
   flag, different behavior.

## Implication: rust-mono's tunnel advantage is structural

rust-mono is built with rustc, which uses an LLVM backend.
If LLVM produced inherently faster code than gcc on parser-
style workloads, the c-xdp2-mono-via-clang variant should
have closed some of the rust-mono tunnel gap. It did not —
clang was 4 ns SLOWER on vxlan-k8s-pure (129 vs gcc's 125).

The rust-mono tunnel advantage must come from language-level
differences, not backend choice:

- **Rust monomorphization**: each generic parse-node trait
  method gets a specialised function per concrete type. The
  C codegen template expands macros at compile time but the
  resulting C code still has function-pointer calls in the
  proto_table dispatch (devirtualised by gcc constant-
  folding, not source-level).

- **Rust's match-tree codegen**: LLVM compiles Rust `match`
  with a structurally different dispatch than C's `switch`.
  rustc's `match` on a `Box<dyn ParseNode>` becomes a vtable
  dispatch + monomorphic body; gcc's `switch (type)` on an
  integer becomes a binary-search tree of compares.

- **Different metadata-struct layout choices** in the rust-
  bench equivalent — fewer fields written per packet,
  smaller per-packet store footprint.

These are all source-language / codegen-template differences,
not backend differences.

## Decision

**c-xdp2-mono stays on gcc.** The clang variant
(`flow-dissector-matrix-artifacts-clang`) remains in the
flake for future experiments but is not the default.

R7-A's hypothesis that LLVM might produce structurally
different (and faster) code on the parser is **disproven on
Zen 1 with this codebase**. The 36 ns rust-mono vxlan
advantage is structural and not closable by C compiler swap.

## Future investigation directions (if pursuing further)

1. **clang-specific optimisation flags**: try `-flto=thin`,
   `-mllvm -inline-threshold=N`, `-fwhole-program-vtables` etc.
   Maybe a non-default clang flag combination produces faster
   code on this specific workload.

2. **PGO (profile-guided optimization)** — option E in
   `docs/perf-next-steps.md`. Either gcc-PGO or clang-PGO
   could close the gap with the right profile. Build
   infrastructure investment.

3. **Per-parser metadata struct** (R6 audit Option C) — the
   structural fix that addresses rust-mono's actual advantage
   (fewer fields written per packet). ~500 LoC IR + codegen.

4. **Rewrite the mono template in Rust** — i.e., make the
   "real" c-xdp2-mono what xdp2-bench's rust-mono mode does.
   Implausible for kernel-team consumption (kernel doesn't
   accept Rust dependencies in flow_dissector yet) but
   interesting research direction.

## Conclusion in one paragraph

XDP2's c-xdp2-mono codegen is gcc-tuned. clang-21 at the same
optimisation flags produces strictly slower code on Zen 1
(+0 to +39 ns/pkt across the 6-workload sweep), with a
dramatic +39 ns regression on PPPoE traffic. The rust-mono
tunnel-workload advantage over c-xdp2-mono is therefore NOT
from LLVM backend choice (which would have helped clang here
too) — it's from Rust source-level structure (monomorphization,
match-tree dispatch, smaller metadata struct). gcc remains the
right compiler choice for c-xdp2-mono; option B from the
next-steps doc is closed as "investigated, negative result".
