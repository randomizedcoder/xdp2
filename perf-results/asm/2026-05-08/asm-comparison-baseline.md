# Cross-Implementation Assembly + Microarchitectural Baseline — 2026-05-08

First end-to-end assembly + microarchitectural comparison across 14
flow-dissector implementations. Closes the gap the user identified:
the PCAP-replay matrix told us *which* implementations are faster;
this baseline tells us *why* at the instruction level.

## Configuration

- **Hardware:** hp5 (AMD Ryzen 5 PRO 2400G, Zen 1, 4C/8T @ 3.6 GHz),
  matches the post-17.E perf headline numbers.
- **PCAP:** combo.pcap (500,000 mixed packets, generated by
  `.#test-pcap`).
- **Iterations:** Rust modes 50 (×500K pkts = 25M parses); C/BPF
  modes 1000 (BPF_PROG_TEST_RUN repeat) ×500K = 500M parses.
- **Parameters:** `xdp2-bench --mode <X> --pcap combo.pcap
  --iterations 50`; `benchmark -n 100`; `benchmark_bpf -n 1000`.
- **llvm-mca target:** `-mcpu=znver1` (Zen 1).
- **perf events:** cycles, instructions, branches, branch-misses,
  L1-dcache-loads, L1-dcache-load-misses, dTLB-loads, dTLB-load-misses.
  LLC-loads / LLC-load-misses unsupported on Zen 1 PMU.

## What this answers — per-pair diff

### **`c-bpf-fast` (18 ns) vs `c-xdp2-usp` (232 ns)** — 13× gap

| | c-bpf-fast | c-xdp2-usp (from c-all-usp) |
|---|---:|---:|
| ins/pkt | 83 | ~466 (avg) |
| IPC (live) | 1.94 | 0.60 |
| branch-miss% | 0.10% | 2.39% |
| static instructions (llvm-mca) | n/a | 6,879 |
| static cycles (llvm-mca) | n/a | 3,294 |
| static IPC ceiling | n/a | 2.09 |

**Story:** `c-bpf-fast` is a hand-curated 7-chain BPF program
(see `samples/flow_dissector/fast_bpf/fast_flow.bpf.c:103-208`).
Each chain is a fixed-offset extractor — eth+ipv4+tcp, eth+ipv4+udp,
etc. — with no encapsulation depth, no flag-fields parsing, no
TLV walk, no metadata reset. The kernel JIT compiles it to a
straight-line sequence of `bpf_skb_load_bytes` + memwrites with
zero indirect calls. The verifier rejected anything more
ambitious, which forced this minimal implementation; that
minimalism IS the speed.

`c-xdp2-usp` runs `__xdp2_parse` (from `libxdp2.so`) which
dispatches per-protocol via the parse-graph node table. Each node
function (`__xdp2_parser_big_*_node_xdp2_parse.isra.0` in
libxdp2.so disasm) does protocol-specific length checks,
sub-protocol lookup via switch/jump-table, then tail-calls the
next node. The static count of **6,879 instructions** captured by
the dump-asm pass spans `__xdp2_parse` + ~20 node functions; the
per-packet hot path through this graph hits roughly 230 of them
on combo.pcap traffic.

Plus the per-packet `memset(meta, 0, 200)` adds ~11 ns
(c-xdp2-usp 232 ns vs c-xdp2-parse-only 221 ns).

The 4× live-instruction gap (83 vs ~466 ins/pkt) plus the
3.2× IPC gap (1.94 vs 0.60) multiplies to the observed 13× ns
gap. Both factors matter; the ins-count win is the bigger one.

### **`c-bpf-flowdis` (91 ns) vs `c-flowdis-usp` (162 ns)** — same algorithm, 1.8× gap

| | c-bpf-flowdis | c-flowdis-usp (in c-all-usp) |
|---|---:|---:|
| ins/pkt | 390 | ~232 |
| IPC (live) | 2.21 | 0.60 |
| static instructions (llvm-mca) | n/a | 3,004 |
| static cycles (llvm-mca) | n/a | 1,275 |
| static IPC ceiling | n/a | 2.36 |

**Story:** SAME algorithm (kernel's `__skb_flow_dissect`). The
JITed BPF version (kernel selftest) executes the EQUIVALENT
parser logic but the JIT scheduler produces tighter code than
gcc -O2 on the same source. The static llvm-mca ceiling for
`c-flowdis-usp` is **IPC 2.36** but the live measurement is
**0.60** — meaning the userspace C compile is leaving 75% of its
static throughput on the table. The BPF JIT delivers 2.21 IPC
in production.

The userspace C version pays for: dynamic linking against
libflowdis.so (PLT trampolines), full-FlowMeta initialization,
no JIT-time loop scheduling. The kernel BPF version has none of
these — it's a JIT pass that sees the whole program and schedules
it as one big basic block.

### **`rust-graph-enum` (17 ns) vs `rust-compiled` (47 ns)** — 2.8× gap, same parser logic

| | rust-graph-enum | rust-compiled |
|---|---:|---:|
| ins/pkt | 327 | 367 |
| IPC (live) | 1.55 | 1.21 |
| branch-miss% | 2.28% | 5.01% |
| static instructions (asm-stats agg) | 9,450 | 10,956 |
| static IPC ceiling (llvm-mca) | 1.70 | 1.89 |

**Story:** graph-enum dispatches via a Rust enum match, producing
a `cmov`-chain or jump-table per node transition. compiled
dispatches via the xdp2-compiler-generated jump-table per node
type. Both eliminate dyn-trait indirect calls.

The instruction-count gap is small (327 vs 367, **11%** more for
compiled). The IPC gap is bigger (1.55 vs 1.21, **28%** higher for
graph-enum). The branch-miss rate is the smoking gun: graph-enum
2.28%, compiled 5.01% — graph-enum's enum-match dispatcher is
**predictable**, the compiled jump-table-of-function-pointers is
not.

That 2.8× ratio (live ns/pkt) doesn't all come from the
instruction + IPC numbers; it's also that the
post-17.E headline 17 ns vs 47 ns came from 100-iter runs at
different bench parameters. The ratio has compressed somewhat at
50 iter on combo.pcap. The directional finding (graph-enum > compiled)
is robust.

### **`c-xdp2-usp` (232 ns) vs `c-xdp2-parse-only` (221 ns)** — 11 ns of memset

| | c-xdp2-usp | c-xdp2-parse-only |
|---|---:|---:|
| static instructions (asm-stats) | 6,837 | 6,423 |
| static cycles (llvm-mca) | 3,294 | 3,051 |

**Story:** the only difference is whether `memset(meta, 0, 200)`
runs **per packet** (c-xdp2-usp) or **once at startup**
(c-xdp2-parse-only). 414 extra static instructions = 1 memset
of 200 bytes (zero-fill is ~12 store-pair ops + 2 stack ops + 2
moves; LLVM unrolls it into ~30 stores in 32-byte chunks). 11 ns
per-packet overhead matches that — at 1.21 IPC × ~3.6 GHz =
4.36 cycles/ns, 11 ns ≈ 48 cycles ≈ 30-50 stores depending on
store-buffer / D-cache hit rate.

This is the cheapest and most isolated optimisation in the table.
Pre-zeroing FlowMeta at the bench-loop level (or making the parser
not require zeroed input) saves 11 ns/packet on every full-XDP2
parse.

## Per-impl deep dive (top observations)

### `c-bpf-fast` — the leader on instruction count

- 83 ins/pkt is a hard floor on this hardware. The BPF program
  only handles 7 hardcoded chain shapes (fast_flow.bpf.c:72-80).
  Anything outside those shapes returns `BPF_FLOW_DISSECTOR_CONTINUE`
  and the kernel slow-path dissector takes over — but on
  combo.pcap, the 7 chains cover ~90% of the traffic.
- Branch-miss rate **0.10%** is exceptional. The fixed-offset
  extractors have only the chain-selection branches at the top;
  inside each chain, the loads are address-known.
- IPC 1.94 means the JIT is using 6 of Zen 1's 4-issue+ uop slots
  per cycle — about half the theoretical ceiling.

### `rust-graph-enum` — the Rust leader

- 327 ins/pkt at 2.3% branch-miss. The enum dispatch is
  `match node { ... }` in source; LLVM lowers it to a jump-table
  AND a few `cmov`s for the simple two-arm cases. Branch-miss
  rate is half of compiled's because the dispatcher is contiguous
  (one switch); compiled dispatches through a function-pointer
  table that the BPU has to learn.
- Branch-miss rate is still 23× worse than c-bpf-fast (2.3% vs
  0.10%). On Zen 1, a mispredicted branch costs ~16-20 cycles —
  at 327 ins/pkt × 2.3% = 7.5 mispredicts × ~18 cycles = 135
  cycles wasted per packet. That's ~37 ns. The current 17 ns/pkt
  number suggests the µarch is hiding most of these via OoO
  speculation; reducing the rate further is leverage.

### `c-flowdis-usp` (kernel C, userspace) — IPC half its ceiling

- 3,004 static ins (lowest static count among C+Rust impls), but
  IPC 0.60 live. Static llvm-mca ceiling: 2.36. **The userspace
  C compile is delivering 25% of its static throughput.**
- Likely cause: the c-all-usp run mixes 3 different impls in one
  perf invocation, so the IPC is averaged across them. Pure
  c-flowdis-usp is probably ~1.0-1.5 IPC on its own. A focused
  per-mode perf run is the immediate follow-up.

### `rust-graph` (dyn-dispatch) — the ceiling

- 1,521 ins/pkt at 4.06% branch-miss. The vtable-driven dispatch
  hits a `call *%rax` per protocol transition; the BPU doesn't
  learn it because the function pointer changes per packet.
- This is the worst-case Rust ranking and matches existing
  documentation in `xdp2-rs/docs/fast-path-dispatch.md`.

### `c-bpf-xdp2` — verifier-rejected on 7.x

- The kernel verifier rejected `flow_dissector.bpf.o` so it never
  loaded — the 320M cycles + 573M instructions in the perf-stat
  is only the loader's failed-to-load path (0.09s elapsed). The
  static dump in `c-bpf-xdp2/static.bpf.asm` shows the LLVM
  compile, but it's never JITed.
- The "why does the BPF compiled by xdp2 fail verification?"
  question is documented in
  `samples/flow_dissector/docs/challenges.md`. Out of scope
  here.

## llvm-mca port-pressure highlights

(Static throughput ceilings on Zen 1; full output in each impl's
`llvm-mca.txt`.)

| Impl | Static IPC ceiling | Live IPC | Headroom |
|---|---:|---:|---:|
| c-flowdis-usp | 2.36 | 0.60 (avg in c-all-usp) | **75%** |
| c-xdp2-usp | 2.09 | 0.60 (avg in c-all-usp) | **71%** |
| c-xdp2-parse-only | 2.12 | 0.60 (avg in c-all-usp) | **72%** |
| rust-compiled | 1.89 | 1.21 | 36% |
| rust-mono | 1.89 | 1.24 | 34% |
| rust-template | 1.91 | 1.14 | 40% |
| rust-graph-enum | 1.70 | 1.55 | **9%** |
| rust-graph | 1.73 | 1.24 | 28% |

**rust-graph-enum is at 91% of its static IPC ceiling.** Further
parser-side optimisations on this mode have diminishing returns.
The remaining wins live in the algorithmic count (the 327 ins/pkt
itself), not in scheduling.

The C-side modes have **70%+ headroom** between static and live
IPC. That gap is real-system stalls — branch mispredicts, dTLB
misses (the 97.5% rate on c-all-usp is striking; the 500K-packet
StoredPacket Vec spans many pages), L1d misses. Each is a
fixable target.

## Optimization recommendations (ranked by leverage)

| # | Target | Expected win | Effort | Why |
|---|---|---:|---:|---|
| 1 | Hoist `memset(meta, 0, 200)` out of the per-packet loop in xdp2-c | **~11 ns** (~5%) | trivial | Already proven by c-xdp2-parse-only. The memset is ~30 stores; eliminate at startup. |
| 2 | Reduce `__xdp2_parse` indirect-call density (libxdp2.so) | ~30-60 ns | medium | The graph-walking dispatcher uses one indirect call per node transition. Inlining the common-case 5-tuple chain (eth/ipv4/{tcp,udp}) would eliminate ~3-4 indirect calls per packet. |
| 3 | Lower rust-graph-enum branch-miss from 2.3% to <0.5% | ~10-15 ns | medium | Currently 23× worse than c-bpf-fast. Look at `xdp2_core::enum_dispatch::engine::parse_enum`; consider profile-guided optimisation hints, or compile-time-known protocol-tag dispatch tables vs runtime match. |
| 4 | Per-mode focused perf-stat (split c-all-usp into 3 runs) | analysis-only | trivial | The 0.60 IPC blended number masks per-mode wins. Re-run perf with `benchmark -p -n 100 --bench flowdis` etc. to get clean per-mode IPC. |
| 5 | Run `dump-asm --with-bpf-jit` on hp5 to capture JITed BPF asm | analysis-only | small | The static llvm-objdump shows BPF bytecode, not the JITed x86 the kernel actually runs. The JIT pass adds register allocation + scheduling that the BPF→x86 cost story depends on. |
| 6 | Eliminate per-packet StoredPacket Vec deref (cause of 80%+ dTLB miss) | analysis-only on PCAP replay; nil on AF_XDP | trivial / not needed | The dTLB miss rate is a PCAP-replay artifact (large Vec spans pages). Live AF_XDP uses contiguous UMEM frames; this number won't translate. |
| 7 | rust-graph: replace dyn-trait vtable with enum-dispatch | ~270 ns | already done as graph-enum | rust-graph is the worst by 4× because of vtable indirect calls. graph-enum already implements the fix. Mark rust-graph as "kept for benchmark comparison only." |

## Reproducing

```bash
# Phase A1+A2 — extract assembly
nix run .#flow-dissector-dump-asm -- --out perf-results/asm/$(date -I)

# Phase A3 — static analysis
nix shell nixpkgs#llvm -c \
    nix/scripts/run-llvm-mca.sh perf-results/asm/$(date -I)/ --mcpu=znver1
python3 nix/scripts/asm-stats.py perf-results/asm/$(date -I)/ \
    --csv perf-results/asm/$(date -I)/static-stats.csv

# Phase A4 — perf-record on hp5 (needs root for some events)
scp nix/scripts/perf-record-impl.sh root@hp5:/tmp/
ssh root@hp5 'cd ~/xdp2 && \
    combo=$(nix build --no-link --print-out-paths .#test-pcap)/combo.pcap && \
    xdp2_rs=$(nix build --no-link --print-out-paths .#xdp2-rs) && \
    art=$(nix build --no-link --print-out-paths .#flow-dissector-matrix-artifacts) && \
    /tmp/perf-record-impl.sh --pcap "$combo" --xdp2-rs "$xdp2_rs" \
        --artifacts "$art" --out /tmp/perf-hp5'
scp -r root@hp5:/tmp/perf-hp5 perf-results/asm/$(date -I)/
python3 /tmp/perf-roll.py perf-results/asm/$(date -I)/perf-hp5/
```
