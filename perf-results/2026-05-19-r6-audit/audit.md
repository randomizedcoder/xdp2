# R6 phase 1 — xdp2_metadata_all field-write audit

## Goal

The 2026-05-19 R5 trim landed three template trims (`last_node`
store, NULL-ops checks, overlay-advance / keyin / len_op gates)
and measured **0 ns/pkt delta on hp5** because gcc
`-O3 -march=native -flto` was already folding those branches.
The conclusion: the remaining ~49 ns gap to rust-mono on
`vxlan-k8s-pure` is in the **data path** — bytes written per
parse to `xdp2_metadata_all` — not in dispatch shape.

R6 = metadata-struct re-layout. This phase 1 audit gathers the
data needed to choose a layout strategy in phase 2.

ipv4 + tcp ports):

| CL | hot bytes written | cold bytes wasted |
|---|---:|---:|
| CL0 (0-63) | 2 (addr_type+bitfields) + 12 (eth_addrs) = 14 | 50 (tcp_options + mpls untouched) |
| CL1 (64-127) | 2 (l3_off) | 62 (arp, gre, gre_pptp, l2_off untouched) |
| CL2 (128-191) | 2+1+4+32 (eth_proto, ip_proto, ports, addrs front) = 39 | 25 (flow_label, vlan, keyid, icmp untouched) |
| CL3 (192-) | 4 (addrs tail) | 4 (struct padding) |

Three cachelines touched per packet to write 55 hot bytes out
of 200 struct bytes. **27 % field-write density, 75 % of the
struct's bytes are zero-traffic on the hottest workload.**

## Per-workload cacheline-touch projection

Composing the per-template profiles into representative parse
chains:

### TCP/IPv4 over Ethernet (no options) — `https-web.pcap`

Chain: `ether` → `ipv4` → `ports`

- eth_proto (2B, CL2) ← ether
- eth_addrs (12B, CL0) ← ether
- l3_off (2B, CL1) ← ipv4
- is_fragment + first_frag (bits, CL0) ← ipv4
- addr_type (1B, CL0) ← ipv4
- ip_proto (1B, CL2) ← ipv4
- addrs.v4 (8B in 32B field, CL2/3) ← ipv4
- ports (4B, CL2) ← ports

**Cachelines touched: 4 (CL0, CL1, CL2, CL3). Hot bytes
written: ~30 B. Wasted bytes per CL: ~170 B.**

### TCP/IPv6 over Ethernet — `tcp_ipv6.pcap` corpus

Chain: `ether` → `ipv6` → `ports`

- eth_proto (CL2), eth_addrs (CL0) ← ether
- l3_off (CL1), ip_proto (CL2), addr_type (CL0), flow_label (CL2), addrs.v6 (32B in CL2+CL3) ← ipv6
- ports (CL2) ← ports

**Cachelines touched: 4. Hot bytes written: ~58 B (more from
v6 addrs).**

### VLAN+TCP/IPv4 — `vlan-tcp-mix.pcap`

Chain: `ether` → `vlan_8021Q` (just tag walk) → `ipv4` →
`ports`. Adds `vlan_count + vlan` write to CL2 if
`vlan_set_tpid` template fires.

**Cachelines touched: 4. Hot bytes written: ~32 B + 10 B
(vlan_count, vlan) = ~42 B.**

### VXLAN inner-walk — `vxlan-k8s-pure.pcap` (the 141-ns target)

Chain (per encap frame): `ether` → `ipv4` → `udp` → `vxlan`
(no extract) → `ether` → `ipv4` → `tcp ports`.

Outer frame (frame[0]): ~30 B written, 4 CLs touched.
Inner frame (frame[1]): ~30 B written, 4 CLs touched.

**Two metadata frames × 4 cachelines × write ≈ 8 cacheline
writes per packet** versus rust-mono's `FlowMeta` (~100 B,
fits in 2 cachelines, ~2 cacheline writes per packet).

That's a 4× cacheline-write multiplier on the tunneled
workload — consistent with the ~280 instr/pkt difference the
icache sweep measured (each cacheline-write store costs ~3-4
instructions + cache traffic).

## Hash invariant constraints

The hash computation
(`XDP2_COMMON_COMPUTE_HASH(frame, eth_proto)`) spans the byte
range `offsetof(eth_proto) ..= offsetof(addrs) + sizeof(addrs)`.
That's bytes 136..196 today — 60 bytes hashed.

```c
#define XDP2_HASH_START_FIELD_ALL eth_proto   /* parser_metadata.h:235 */
#define XDP2_METADATA_addrs ... /* Must be last */  /* :244 */
```

This means **any layout change must preserve the byte content
of the eth_proto..addrs range, or every existing flow-hash
value changes** (breaks downstream consumers tied to hash
output). The hashed range is the union of `eth_proto`,
`ip_proto`, `flow_label`, `vlan`, `keyid`, `ports`, `icmp`,
`addrs`. We can't reorder fields within that range without
changing the hash.

Fields BEFORE `eth_proto` (the entire CL0+CL1 region: addr_type,
bitfields, eth_addrs, tcp_options, mpls, arp, gre, gre_pptp,
l2_off, l3_off, l4_off) are NOT hashed. They can be freely
reordered.

Fields AFTER `addrs` would also not be hashed. The "must be
last" comment is enforced by the `XDP2_HASH_LENGTH` macro
which assumes `addrs` is contiguous with the hash region and
ends it.

## Layout options for R6 phase 2

### Option A — Trailing-cold reorder (no hash change)

Move large cold fields (`tcp_options`, `arp`, `gre`,
`gre_pptp`) to AFTER `addrs`. Keep hash region byte-identical.

Per-workload outcome for https-web (TCP/IPv4):
- Hash region still in CL2-CL3 → 2 cachelines for hot writes
- eth_addrs (CL0) still touched → 3 cachelines total instead of 4
- tcp_options moves to CL3-CL4+ region, untouched on no-options TCP

**Net per-packet write savings**: ~1 cacheline drop on most
workloads (CL1 becomes write-cold).

**Cost**: ~5-line struct reorder, no API break, no hash break.

### Option B — Hot-cacheline coalescence (breaks hash compat)

Pack all hot fields (eth_addrs, eth_proto, ip_proto, l3_off,
l4_off, ports, addrs, addr_type, bitfields) into the first
cacheline (~57 B fits). Move ALL cold fields to tail.

Per-workload outcome for https-web:
- Hash region content reorganized → **hash output changes**
- 1 cacheline write for hot path (vs 3 today)

**Cost**: Requires updating `XDP2_HASH_START_FIELD_ALL` and
re-baselining all hash-dependent tests. Probably 2-3 day
effort, surfaces externally as "v2 hash format".

### Option C — Per-parser tailored struct (codegen-driven)

Each parser declares its used field set in its
`xdp2_parser_def`; the codegen emits a tailored
`struct <parser_name>_metadata` containing only those fields.
`struct xdp2_metadata_all` becomes the union/superset for
parsers that don't opt in.

Per-workload outcome:
- flow-dissector-l2 declares `{eth_addrs, eth_proto, ip_proto,
  addr_type, bitfields, l3_off, ports, addrs}` → ~57 B struct,
  1 cacheline.
- vxlan parser declares the same set → 1 cacheline per frame.
- ARP-specific parser declares `{arp, eth_addrs}` → small struct.

**Cost**: ~500 LoC across IR (used-field tracking),
graph_consumer (capture field usage), codegen (emit per-parser
struct + extractor signatures), AND every site that today
writes `struct xdp2_metadata_all *` must take a
`void *frame` with a parser-provided struct definition. API
surface change is large.

## Recommendation

**Phase 2A: Try Option A first** as a fast-feedback experiment.
~5 line change, no API break, no hash break, runs through the
matrix + parity-gate cleanly. If it moves ns/pkt on hp5, that
confirms the hypothesis and we ship it.

If Option A delta is ≤2 ns/pkt (noise), Option B becomes the
next candidate (the bigger reorder is needed to coalesce all
hot writes into one CL). If Option B delta is ≤5 ns/pkt,
Option C (per-parser struct) is the only remaining headroom
and that justifies the larger API change.

## Reproduction

Field layout probe:
```sh
gcc -O0 -I src/include -include xdp2/parser_metadata.h \
    /tmp/metadata-layout-probe.c -o /tmp/probe
/tmp/probe
```

Per-template field-write extraction:
```sh
awk '
/^#define XDP2_METADATA_TEMP_/ {
    in_macro = 1; name = $2; sub(/\(NAME.*/, "", name); fields[name] = ""; next
}
in_macro {
    line = $0
    while (match(line, /frame->[A-Za-z_][A-Za-z0-9_]*/)) {
        f = substr(line, RSTART+7, RLENGTH-7)
        if (!seen[name SUBSEP f]) { seen[name SUBSEP f] = 1; fields[name] = fields[name] " " f }
        line = substr(line, RSTART + RLENGTH)
    }
    if ($0 !~ /\\$/) in_macro = 0
}
END { for (n in fields) printf "  %-32s %s\n", n, fields[n] }
' src/include/xdp2/parser_metadata.h | sort
```
