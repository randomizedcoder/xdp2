# T-afxdp — AF_XDP live load sweep on hp2 → hp5

Generated by `nix run .#flow-dissector-afxdp-live -- --testbed
testbeds/hp2-hp5-x710.toml --duration 30 --loads 1,2,5,10` (Phase 15).

**Topology:** kernel pktgen on `hp2` (peer) → 10 GbE fibre → Intel X710
i40e Flow Director (UDP/443 → queue 1) on `hp5` (DUT) → native XDP
(`xdpdrv`) → AF_XDP zero-copy → `xdp2-bench --mode af-xdp-template`
dispatching through `EthIpv4Udp` template with no software
classification.

**Per-load measurements (30 s, 1400-byte pktgen frames, native XDP +
zero-copy + busy-poll 50 µs):**

| Offered (Mpps) | Received (pps) | Mpps received | Drops % | Zerocopy |
|---------------:|---------------:|--------------:|--------:|----------|
| 1              | 877 786        | 0.88          | 12.22 % | yes      |
| 2              | 877 789        | 0.88          | 56.11 % | yes      |
| 5              | 877 804        | 0.88          | 82.44 % | yes      |
| 10             | 877 806        | 0.88          | 91.22 % | yes      |

**Key finding:** the AF_XDP receiver caps at ~877 K pps (= 0.88 Mpps)
regardless of offered load. Drops scale linearly with offered load
because the difference between offered and received is exactly the
delta. Increasing pktgen rate doesn't help — the receiver ring/fill
side is the bottleneck, not the sender.

This is the documented **D3 RX-drop issue** (see
`docs/physical-testbed.md` §"Per-experiment matrix (Deliverables 1, 2,
3)"): the default AF_XDP fill ring (2048 descriptors) and frame count
(4096) are too tight at ≥1 Mpps with busy-poll. The D3 experiments
(`xdp2-exp-afxdp-rings-large`, `xdp2-exp-afxdp-busypoll-100`,
`xdp2-exp-afxdp-netdev-budget`) explore tunable fixes but were not
re-run as part of this phase.

**Plan §15 DoD vs reality:**
- "At 1 Mpps offered: drops < 0.1 %" — **not met**: drops 12.2 %.
  This is the documented D3 receiver-side ceiling, not a Phase 15
  wrapper bug. The Phase 15 deliverable is the load-sweep
  measurement; the < 0.1 % target is a follow-up tuning effort
  blocked on D3.
- Per-load JSONs under `<results>/<date>/<testbed>/afxdp/` — **met**.
- AF_XDP zerocopy detected on every cell — **met**.

**Pktgen-side caveat:** pktgen was driven at default `burst=1`, not
the `burst=32` + per-thread `queue_map_min/max` setup that the
2026-04-25 D1 results showed lifts pktgen TX to ~14 Mpps. The
afxdp-live wrapper doesn't currently expose those tunables; if a
future revision wants to drive higher offered loads, the pktgen
section in `samples/flow_dissector/run_ntuple_template_bench.sh`
would need a `PKTGEN_BURST` / `PKTGEN_QUEUE_MAP_MODE` knob to
match the D1 experiment configuration.

## Per-load artifacts

Each load directory under `<results>/<date>/<testbed>/afxdp/`
contains:
- `<L>mpps.json` — wrapper-extracted summary (the table above).
- `<L>mpps.log` — full bench stdout including the per-queue
  template table and pktgen final counters.
- `<L>mpps-bench/` — bench result dir with `ntuple-rules.txt`,
  `pktgen-final-status.log`, `pktgen-start.log`,
  `xdp2-bench-af-xdp-template.txt`. These are the input data for
  the D1 + D3 tuning experiments.
