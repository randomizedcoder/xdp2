# hp5 Perf Targets — Post-R3.4 Run

Drafted 2026-05-19 as a side-by-side comparison of the current
R3.4.5a hp5 baseline against the predicted state after the 14
commits landed since on `merge/matrix-physical-testbed`. Used to
size the next hp5 testbed run and define pass/fail criteria.

## TL;DR

- **No regression expected on the existing `https-web` workload.**
  c-xdp2-mono should stay at ~71 ns/pkt (hp5) — the TCP fast-path
  is unchanged. The UDP-from-fast-path drop, the npi_simple bswap
  fix, the icmp_id sentinel alignment, and the R3.4.4
  generalization are all neutral on a TCP-dominant workload.
- **New workloads (VLAN, PPPoE) should hit the new fast-paths**
  and beat the slow-path generic engine by a similar margin to
  R3.4.1 on plain eth+ipv4+tcp.
- **Tunnel workloads (VXLAN/Geneve/GTP-U) should now be CORRECT
  but a few ns slower** — mono now walks the full inner stack
  instead of short-circuiting at outer UDP.

## Predicted hp5 deltas

### `https-web.pcap` (existing workload)

| Mode | baseline | predicted | delta | reason |
|---|---:|---:|---:|---|
| c-xdp2-mono | 71 | 71 ±1 | none | TCP fast-path unchanged |
| c-xdp2-usp | 135 | 135 ±1 | none | no graph engine changes |
| c-xdp2-parse-only | 135 | 135 ±1 | none | no graph engine changes |
| c-flowdis-usp | 119 | 119 ±1 | none | external library |
| rust-* | (per baseline) | (per baseline) | none | rust changes are bench-side, not parse-path |
| c-bpf-fast | 23 | 23 ±1 | none | BPF program unchanged |

**Pass criterion**: c-xdp2-mono ≤ 75 ns/pkt on hp5 (=baseline ± 5%).
**Fail criterion**: c-xdp2-mono > 80 ns/pkt would indicate a TCP
fast-path regression introduced by one of the R3.4.4 / R3.4.5e
refactorings. Bisect on the 7 listed commits.

### New workloads worth adding to the matrix runner

The R3.4.5b/c/d/e chains and the VXLAN inner walk have no
coverage in the existing 3 workloads (https-web, nfs-server,
k8s-microservices are mostly TCP/IPv4 + a slice of VXLAN). To
exercise them on hp5, add:

| pcap | exercises | expected mono ns/pkt | rationale |
|---|---|---:|---|
| `vlan-tcp-mix` (new) | R3.4.5b (eth+vlan+ipv4+tcp), R3.4.5c (eth+vlan+ipv6+tcp) | 8–12 | VLAN+IPv4+TCP fast-path is +4 bytes vs plain — costs ~1 ns vs R3.4.1 |
| `pppoe-isp` (new) | R3.4.5d/e (eth+PPPoE+ipv4/6+tcp) | 10–14 | PPPoE adds 8 bytes; consumer ISP traffic pattern |
| `vxlan-k8s-pure` (new) | mono full slow-path walk through VXLAN | 20–30 | post-UDP-fast-path-drop tunnel walking; should match c-xdp2-usp ±10% per the mono parity ceiling gate |
| `data/pcaps/broad-coverage.pcap` (existing) | mixed: 520 combinations × 10 packets | 30–60 | catch-all; tests fast-path hit-rate across the chain set |

**Generating the new pcaps**: extend
`samples/flow_dissector/gen_workload_pcap.py` with new entries:

```python
"vlan-tcp-mix": [
    (40, lambda: build_eth_vlan_ipv4_tcp(dport=443, server_side=True)),
    (25, lambda: build_eth_vlan_ipv4_tcp(dport=443, server_side=False)),
    (15, lambda: build_eth_vlan_ipv6_tcp(dport=443, server_side=True)),
    (10, lambda: build_eth_vlan_ipv4_tcp(dport=80, server_side=True)),
    (10, lambda: build_eth_vlan_ipv4_icmp()),
],
"pppoe-isp": [
    (50, lambda: build_eth_pppoe_ipv4_tcp(dport=443, server_side=True)),
    (20, lambda: build_eth_pppoe_ipv4_tcp(dport=443, server_side=False)),
    (15, lambda: build_eth_pppoe_ipv6_tcp(dport=443, server_side=True)),
    (10, lambda: build_eth_pppoe_ipv4_tcp(dport=80, server_side=True)),
    ( 5, lambda: build_eth_pppoe_ipv4_icmp()),
],
"vxlan-k8s-pure": [
    # All VXLAN-encapped (no plain). Forces mono through the
    # slow path so we can measure the cost of full inner walking
    # vs the previous outer-only short-circuit.
    (60, build_k8s_vxlan_grpc),
    (25, build_k8s_vxlan_kafka),
    (10, build_k8s_vxlan_icmp),
    ( 5, build_k8s_liveness_probe),
],
```

The `build_eth_vlan_*` and `build_eth_pppoe_*` helpers don't yet
exist; ~20 lines each, mirroring the existing `build_eth_ipv4_tcp`
helper in the same file.

### `broad-coverage.pcap` (existing, discovery)

Not currently in the matrix runner's perf loop, but a worthwhile
addition. Numbers per parser will look noisy because the workload
covers 520 different packet shapes — most are not fast-path
eligible (esp, ah, sctp, dccp, ospf, etc.). Useful for catching
regressions in the slow path; ~30–60 ns/pkt for c-xdp2-mono.

## What the run will tell us

1. Whether the TCP fast-path number on `https-web` regressed
   (predicted: no).
2. (If new workloads added) the actual cost of the new VLAN /
   PPPoE / VXLAN-slow-path chains on hp5.
3. (If `broad-coverage.pcap` added) the slow-path average across
   the wider protocol surface — useful as a regression sentinel
   for future codegen work.
