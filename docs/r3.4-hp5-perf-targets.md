# hp2/hp5 Perf Targets — Post-R3.4 Run

Drafted 2026-05-19 as a side-by-side comparison of the current
R3.4.5a hp5 baseline against the predicted state after the 14
commits landed since on `merge/matrix-physical-testbed`. Used to
size the next hp5 testbed run and define pass/fail criteria.

## ⚠️ This is NOT apples-to-apples — read first

The ns/pkt numbers in this doc and the R3.4.5a baseline compare
parsers in their **default scope**. Different parsers do
**different amounts of work per packet** by design. Treating "mono
5 ns/pkt vs flowdis 20 ns/pkt = 4× faster" as a like-for-like
benchmark is misleading. The honest framing is "mono is 5 ns/pkt
producing N fields and following tunnels; flowdis is 20 ns/pkt
producing M < N fields and stopping at the outer 5-tuple." The
ratios are still useful, but read them as ceiling indicators, not
as proof one parser is K× the other's speed at equivalent work.

Specifically, these aren't equalized across parsers:

| dimension | c-flowdis-usp | c-xdp2-mono | rust-mono | rust-template |
|---|---|---|---|---|
| metadata field count | 5 | 11+ | 15+ | 8+ |
| tunnel walking | outer only | inner-walks | inner-walks | outer only |
| acceptance scope | kernel set | full graph | full graph | template-matched only |
| starting layer | L2 dispatch | L2 dispatch | L2 dispatch | fixed offsets |
| metadata struct size | ~64 B | ~200 B | varies | ~64 B |
| fast-path hit-rate | n/a | workload-dependent | none | template-match-dependent |

The mono numbers also embed a workload-dependent fast-path hit
rate: a 100%-TCP workload sees the 5 ns headline; a tunnel-heavy
workload walks the slow path at ~19 ns. The single number elides
the distribution.

**Planned follow-up: equal-work + extras-cost decomposition.**
After this hp5 run lands, the next planning item is to add a
second perf mode that times each parser doing the **same** work
(intersected field set + same depth), then reports the **extra**
work XDP2 does (deeper walking + extra fields) and what that
extra costs separately. This is the comparison the Linux kernel
team would want — equal-work demonstrates parser efficiency at
parity; extras-cost demonstrates what richer scope buys. Neither
reduces XDP2's functionality — both modes run side-by-side.

See "Future work" at the end of this doc for the sketch.

## TL;DR

- **No regression expected on the existing `https-web` workload.**
  c-xdp2-mono should stay at ~69–71 ns/pkt (hp2/hp5) — the TCP
  fast-path is unchanged. The UDP-from-fast-path drop, the
  npi_simple bswap fix, the icmp_id sentinel alignment, and the
  R3.4.4 generalization are all neutral on a TCP-dominant workload.
- **New workloads (VLAN, PPPoE) should hit the new fast-paths**
  and beat the slow-path generic engine by a similar margin to
  R3.4.1 on plain eth+ipv4+tcp.
- **Tunnel workloads (VXLAN/Geneve/GTP-U) should now be CORRECT
  but a few ns slower** — mono now walks the full inner stack
  instead of short-circuiting at outer UDP.
- **hp2 vs hp5 delta is itself useful.** Both hosts are CPU-
  identical Ryzen 5 PRO 2400G Zen 1; hp2 has DDR4 @ 2133 MT/s
  vs hp5 @ 1866 MT/s. The hp2/hp5 ns-per-pkt delta per workload
  is a direct measure of memory-bandwidth pressure (compute-bound
  → ≤ 3 % delta; memory-bound → ~14 %). At the R3.4.5a baseline
  XDP2's parse loop showed ~3 % delta = compute-bound. Watch for
  workloads where this delta widens — those are candidates for
  Phase R6 metadata-write trimming.

## hp2 vs hp5 — memory-speed sensitivity axis

The `hp2-hp5-x710` testbed runs the parser benchmark on **both
hosts** (hp5 = DUT, hp2 = generator; but the matrix runner
collects per-host perf data on both via ssh). Per
`docs/physical-testbed.md:124-138` the two hosts are CPU-
identical (Ryzen 5 PRO 2400G Zen 1) but RAM-asymmetric:

| host | DIMMs | clock |
|---|---|---|
| hp2 | 4× 8 GiB DDR4 | **2133 MT/s** |
| hp5 | 4× 16 GiB DDR4 | **1866 MT/s** |

That's a ~14 % theoretical memory-bandwidth gap (hp2 faster).
The R3.4.5a baseline showed only 3 % (hp2 69 ns vs hp5 71 ns on
c-xdp2-mono) — well within run-to-run noise. The parse loop is
**compute-bound**, not memory-bound, at this scope.

**Why this is useful for the kernel-team analysis.** The hp2 vs
hp5 delta per parser per workload tells us how memory-pressure-
sensitive each configuration is:

  - Δ < 5 % → compute-bound (per-instruction efficiency dominates)
  - Δ ≈ 14 % → fully memory-bound (memcpy / cacheline write costs
    dominate; parse loop is starved on memory)
  - Δ in between → mixed; the parser is writing enough metadata
    to start saturating memory bandwidth

The Mode A (equal-work) vs Mode B (extras-cost) split discussed
below will get extra value from hp2/hp5: if Mode A is compute-
bound on both hosts but full-scope shows >5 % hp2 advantage,
**that's a direct measure of how much memory pressure the extras
add** — independent of any single parser's design.

This is also why dropping UDP from the mono fast-path (commit
a063bfc, which made tunnel walks ~10 ns longer) needs a
hp2-vs-hp5 check: the slow-path tunnel walk does ~3× the metadata
writes of the fast-path. If that change pushed the workload into
memory-bound territory, hp2 should show a bigger advantage post-
fix than pre-fix.

### Predicted hp2 vs hp5 deltas

| workload | predicted Δ (hp2 faster) | reading |
|---|---:|---|
| https-web (TCP, fast-path) | ≤ 3 % | unchanged — compute-bound |
| vlan-tcp-mix (fast-path) | ≤ 3 % | same |
| pppoe-isp (fast-path) | ≤ 3 % | same |
| vxlan-k8s-pure (slow-path tunnel walk) | 5–10 % | likely starting to push memory; full inner walk writes ~2-3× the bytes |
| broad-coverage.pcap (mixed) | 4–8 % | mixed, depends on fast-path hit rate |

If the actual hp2-vs-hp5 deltas significantly exceed these
predictions, the metadata-write path is more expensive than
modeled and merits a Phase R6-style trim (parser_metadata.h
optimisation, struct re-layout, etc.).

```

```

```
TB=testbeds/hp2-hp5-x710.toml
for w in https-web nfs-server k8s-microservices \
         vlan-tcp-mix pppoe-isp vxlan-k8s-pure; do
    PCAP=$(nix build .#workload-pcap-$w --no-link --print-out-paths)/$w.pcap
    XDP2_MATRIX_PCAP=$PCAP \
        nix run .#flow-dissector-matrix-run -- --testbed $TB
done
```

Optional `--smoke` for the abbreviated iteration count. Result
tree lands in `perf-results/<date>/hp2-hp5-x710/<host>/` with

What the run will **not** tell us:

- Whether mono is actually K× more efficient than flowdis at the

  code" with "more (or less) work done." See the "Future work"
  section for the planned equal-work bench.

## Future work — equal-work + extras-cost decomposition

The current matrix runner compares each parser in its **default
scope**: every parser produces whatever metadata its design says
it should. That gives a useful ceiling number, but the cross-
parser ns/pkt ratios mix two effects:

  (a) per-instruction efficiency of the parse loop
  (b) how much work each parser is doing

To separate them, the next planning item adds two perf modes
side-by-side with the current "default-scope" mode:

### Mode A — "equal-work"

Each parser is configured to extract **only the intersected
field set** that all parsers agree on (the parity scope's
`bpf_flow_keys` tier: `addr_type`, `ip_proto`, `ipv4_src/dst`,
`ipv6_src/dst`, `sport`, `dport`, `thoff`) and to **stop at the
same depth** flowdis would stop at (= outer 5-tuple). Pass-rate
is restricted to packets ALL parsers accept (a derived "perf-fair"
pcap subset).

This isolates effect (a) — pure parser efficiency at equivalent
work. The hp5 number from this mode is what a kernel-team reader
should compare against the kernel's flowdis: "is XDP2's
generated code more efficient than flowdis's hand-written code
at the same job?"

### Mode B — "extras-cost"

Full-scope XDP2 (everything it normally extracts and walks) minus
the equal-work cost from Mode A. The delta is the **cost of
XDP2's extras**: tunnel-inner walking, additional metadata fields
(l2_off/l3_off/l4_off, vlan[], gre_keyid, icmp_id sentinel,
flow_label, addr_type enum, etc.).

The hp5 number from this mode tells the kernel-team reader: "if
you want N more fields and inner-tunnel walking, here's what
that costs you per packet — and it's still under the kernel
flowdis ceiling."

### Decomposition shape

```
           Mode A          Mode B            Mode A+B
parser     equal-work      extras-cost       full-scope (today)
---        ----------      -----------       ------------------
flowdis    X ns/pkt        n/a (same scope)  X ns/pkt
mono       Y ns/pkt        Z ns/pkt          Y + Z ns/pkt
rust-mono  ...             ...               ...
```

For the same packet, kernel-team readers get:
  - apples-to-apples comparison Y vs X (Mode A)
  - what XDP2's extras buy (Z, isolated)
  - what the full XDP2 stack costs (Y+Z = today's headline)

### Cross-axis: hp2 vs hp5 on each mode

Crossed with the hp2/hp5 memory-speed axis (above), each cell
in the decomposition table becomes a 2×1 sub-table:

```
                Mode A (equal-work)         Mode B (extras-cost)
                hp2     hp5    Δmem         hp2     hp5    Δmem
flowdis         X1      X2     small        n/a     n/a    n/a
mono            Y1      Y2     small        Z1      Z2     larger?
```

The `Δmem` column directly reports memory-bandwidth sensitivity
per mode per parser. Kernel-team reading: "XDP2 mono is N % faster
than flowdis at the same work (Mode A) AND scales no worse with
memory speed (Δmem small). The richer extraction (Mode B) costs
Z ns/pkt and is M % memory-sensitive — here's the budget
tradeoff."

That's three orthogonal signals (parser efficiency, extras cost,
memory sensitivity) on one table, all derived from the existing
two-host testbed.

XDP2's default behavior does NOT change. Mode A is a benchmark-
only configuration (compile-time gated or runtime flag) that
de-tunes the parser specifically for the comparison. Production
users get the full scope; benchmark consumers get the choice.

### Implementation sketch (not yet committed)

- `parity_scope.json` already declares the `bpf_flow_keys` tier
  and per-parser scope intersections. Reuse it.
- Add a `XDP2_BENCH_SCOPE_TIER=bpf_flow_keys` env var to
  `xdp2-bench` and `benchmark.c` that (a) skips field writes
  outside the tier and (b) caps tunnel-walking depth.
- Add a `perf-fair` pcap derivation per workload: feed the
  workload pcap through parity-check, output only the all-
  accept packet indices.
- Extend `flow-dissector-matrix-aggregate` to emit a third
  table column "equal-work ns/pkt" alongside the default-scope
  one, plus a derived "extras delta" column.

Effort estimate: ~200-300 LoC across the bench harness + Nix
wiring + aggregator. Planning happens after this hp5 run lands;
the run is needed to establish the baseline that Mode A will
de-tune against.
