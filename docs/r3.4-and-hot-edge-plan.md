# R3.4 Template Fast-Path + Hot-Edge Ordering — Plan

Two follow-on phases identified after R3.5.2's hp5 sprint showed that
extending IR coverage doesn't move the `c-xdp2-mono` headline (gcc +
LTO was already inlining the indirect `extract_metadata` calls). See
`xdp2-rs/docs/dispatch-architecture-cost.md` §R3.5.2 for the
empirical finding and the revised follow-up priority.

This document plans:
- **R3.4** (HIGH leverage) — template-emitted fast-path
- **Hot-edge ordering** (medium leverage) — R2 gap #3

Both build on the R3.3 generator scaffolding and the R3.5.2 LLVM IR
infrastructure.

## Working assumptions

- `c-xdp2-mono` is the canonical mono parser (R3.3.7). The R3.4
  fast-path lives in `mono_def.template.c` and emits inline at the
  top of the generated entry function.
- Hot-edge ordering also lives in the template (sort the switch arms
  by hit-priority before emission).
- All work continues on `merge/matrix-physical-testbed`.
- Parity gate (`nix build .#checks.parity-gate`, 22-PCAP corpus)
  stays green at every commit; the R3.3.4 regression that escaped
  compile-only verification is the cautionary tale (see
  `xdp2-rs/docs/dispatch-architecture-cost.md` §R3.3 "The IR-coverage
  bug" and the R3.3.4b fix).

## Headline targets

| | https-web ns/pkt today | R3.4 target | Hot-edge target |
|---|---:|---:|---:|
| `c-xdp2-mono` (hp5) | 116 | 23–30 (on >80% common-chain pcaps) | 110–115 (small win on https-web) |
| `c-bpf-fast` baseline | 23 | — | — |
| `c-flowdis-usp` ceiling | 119 | — | — |

R3.4's mono number is workload-dependent (only beats current mono
when the fast-path hits ≥50% of packets). Hot-edge ordering's win is
smaller but applies to every workload.

## R3.4 — Template-emitted fast-path

### Goal

Have the xdp2-compiler emit a hardcoded straight-line extractor for
the common-case packet chain (eth+ipv4+{tcp,udp,icmp}, etc.) at the
top of the generated mono entry function. Reach `c-bpf-fast`'s
23 ns/pkt floor on workloads where the chain shape covers the
majority of packets, while preserving the mono parser's graph
fallback for everything else.

### Why this beats wider IR coverage

R3.5.2 proved that gcc + LTO inlines the indirect
`extract_metadata` calls effectively at -O2, so devirtualising more
patterns doesn't measurably help. The remaining ~93 ns headroom
(mono 116 → c-bpf-fast 23) comes from the parse graph itself: graph
walking, length checks per node, ops-table indirection, encap-depth
tracking. A hardcoded fast-path sidesteps ALL of that for the
common case.

### Design

Two layers:

1. **Fast-path emission** in `mono_def.template.c`: at the top of
   the generated `parser_name_xdp2_parse_mono()` function, emit a
   straight-line block that:
   - Checks `len >= 14 + 20 + 20` (eth + ipv4 + tcp/udp/icmp min)
   - Checks `etype == ETH_P_IP`
   - Checks `ipv4 version=4, IHL=5, no fragment, ip_proto in {6, 17, 1}`
   - Writes the metadata fields the chain produces (l3_off, ip_proto,
     v4_addrs, ports — straight-line, no function calls)
   - Returns `XDP2_STOP_OKAY`
   - On any fail, falls through to the existing `goto label_<root_node>`
     (the mono graph body)

2. **Chain detection** (which chain to fast-path): for the first
   iteration, hardcode the chain selection in the template by
   checking parser metadata. The chain is "eth/ipv4/{tcp,udp,icmp}"
   for the L2 parser. Future iterations can have multiple chains
   (mirroring `c-bpf-fast`'s 7-chain shape) or take a chain
   declaration from the parser source.

### Concrete sketch of phase R3.4.1 template emission

At the top of the generated `<root>_xdp2_parse_mono()` function,
before the existing `goto label_<root_node>;`:

```c
/* R3.4 fast-path: eth+ipv4+{tcp,udp,icmp} common chain.
 * Falls through to the standard graph body on any mismatch. */
if (len >= 14 + 20 + 4) {
    const __u8 *p = (const __u8 *)hdr;
    __be16 etype = *(const __be16 *)(p + 12);
    if (etype == htons(ETH_P_IP)) {
        const struct iphdr *iph = (const void *)(p + 14);
        /* Reject IHL != 5 (options), fragments, and non-{tcp,udp,icmp} */
        if (((const __u8 *)iph)[0] == 0x45 &&
            !(((const __u8 *)iph)[6] & 0x3f) && /* frag_off lo bits */
            !(((const __u8 *)iph)[7]) &&         /* frag_off hi bits */
            (iph->protocol == IPPROTO_TCP ||
             iph->protocol == IPPROTO_UDP ||
             iph->protocol == IPPROTO_ICMP)) {
            struct xdp2_metadata_all *_meta = metadata;
            _meta->addr_type = XDP2_ADDR_TYPE_IPV4;
            _meta->l3_off = 14;
            _meta->ip_proto = iph->protocol;
            *(__u64 *)&_meta->addrs.v4_addrs = *(const __u64 *)((const __u8 *)iph + 12);
            if (iph->protocol != IPPROTO_ICMP) {
                /* TCP/UDP: ports at iph + 20 */
                _meta->port16[0] = *(const __be16 *)((const __u8 *)iph + 20);
                _meta->port16[1] = *(const __be16 *)((const __u8 *)iph + 22);
            } else {
                /* ICMP: type/code/id */
                const __u8 *icmp = (const __u8 *)iph + 20;
                _meta->icmp.type = icmp[0];
                _meta->icmp.code = icmp[1];
                _meta->icmp.id = *(const __be16 *)(icmp + 4);
                if (_meta->icmp.id == 0) _meta->icmp.id = htons(1);
            }
            return XDP2_STOP_OKAY;
        }
    }
}
/* Fast-path miss — fall through to the standard graph body */
```

(Pseudo-template — real version uses `<!--(if ...)-->` gates around
the parser-name and emits the actual metadata struct field offsets
from the IR.)

### Verification

```
nix build .#flow-dissector-matrix-artifacts
nix build .#checks.parity-gate                  # must stay 22/22 ok
nix run .#flow-dissector-matrix-run -- \
    --testbed testbeds/hp2-hp5-x710.toml \
    --results perf-results/2026-05-Xx-r3.4/
```

Headline metric: `c-xdp2-mono` ns/pkt on hp5 https-web. Bounds:
- Hard floor: ≥ `c-bpf-fast` (23 ns) — fast-path can't outperform the
  JIT'd BPF version on its own ground.
- Soft target: ≤ 40 ns if chain hits ≥50% of packets.
- Failure: > 116 ns (current mono number) — would mean the fast-path
  miss-check is more expensive than the saved graph walk.

### Risks

1. **Parity bugs from off-by-one in the fast-path.** The hand-written
   shape is straight-line and bug-prone (byte offsets, htons usage,
   icmp.id sentinel). Mitigation: bake in `c-bpf-fast`'s exact
   metadata-write order as a reference.
2. **Fast-path miss cost.** Each packet pays the bounds-check +
   etype-check + ipproto-check before falling through. On a workload
   where the chain rarely hits (e.g. IPv6-only traffic), this overhead
   adds to the slow path. Measure on QinQ, ipv6-only pcaps.
3. **Chain choice is wrong for the workload.** Hardcoding
   eth+ipv4+l4 means IPv6-heavy or VLAN-heavy traffic gets zero benefit.
   R3.4.4's `XDP2_FAST_PATH_CHAIN()` annotation addresses this but is
   bigger work.

## Hot-edge ordering (R2 gap #3)

### Goal

Sort the switch arms in the generated mono `next_proto` dispatch by
hit-frequency, so common protocols (TCP, UDP, ICMP, IPv4, IPv6) are
the first cases the branch predictor sees. Currently arms are emitted
in declaration order from the proto_table — TCP might be the 5th
case rather than the 1st.

### Why this still matters after the R3.5.2 finding

The R3.5.2 finding ("LTO already inlines extract_metadata") doesn't
apply here. Branch-prediction behavior is determined by the order
the switch arms appear in the generated source; LTO has nothing to
optimise once gcc emits a jump table. Reordering at codegen time is
the only knob.

The plan-file table from R3.5 estimated this as a "medium" perf
win — likely 2–5% on `c-xdp2-mono` on https-web (where TCP/UDP
dominate but aren't currently the first arms in the dispatch).

### Design

Per-edge hot-priority value, precomputed in the Python template
preprocessor (`template.cpp` `generate_parser_function`):

```python
HOT_PRIORITY = {
    # IP protocols (in ipv4/ipv6 next-proto dispatch)
    'IPPROTO_TCP':   100, 'IPPROTO_UDP':   100, 'IPPROTO_ICMP':   80,
    'IPPROTO_ICMPV6': 80, 'IPPROTO_GRE':    40, 'IPPROTO_IPV6':   40,
    'IPPROTO_IPIP':   40, 'IPPROTO_ESP':    20, 'IPPROTO_AH':     20,
    # Ethertypes (in etype dispatch)
    'ETH_P_IP':       100, 'ETH_P_IPV6':    100, 'ETH_P_ARP':      40,
    'ETH_P_8021Q':    80, 'ETH_P_8021AD':   80, 'ETH_P_MPLS_UC':  40,
    'ETH_P_PPP_SES':  40, 'ETH_P_RARP':     20,
    # Anything else defaults to 0
}
```

Per-edge: lookup `edge['macro_name']` in HOT_PRIORITY, default 0.
Stash on the edge dict. In the template, replace the for-loop over
`graph[node]['out_edges']` with a sorted version (descending by
hot_priority).

### Phase breakdown

| Phase | Scope | Files | LoC | Risk |
|---|---|---|---|---|
| H1 | Hardcode HOT_PRIORITY table in `template.cpp`'s Python preprocessor; sort `out_edges` per vertex by descending priority; expose sorted list as `out_edges_hot_sorted`. | `src/tools/compiler/src/template.cpp` | ~40 | Low |
| H2 | Update `mono_def.template.c` to iterate `out_edges_hot_sorted` instead of `out_edges`. Diff inspection: generated parser.mono.c should show TCP / UDP arms before encap arms in IPv4/IPv6 dispatch switches. | `src/templates/xdp2/mono_def.template.c` | 1 (rename the loop variable) | Low |
| H3 | Parity gate + matrix sprint. Expect: parity 22/22 (reordering arms is semantically equivalent), and a 2–5% perf delta on c-xdp2-mono. | `nix build`, `flow-dissector-matrix-run` | 0 | Low |

Total: ~40 LoC across 3 commits, all low-risk.

### Verification

```
nix build .#flow-dissector-matrix-artifacts
# Spot-check generated switch arms — TCP first, ESP last:
grep -A30 "next_proto load.*ipv4_node\|case IPPROTO_TCP\|case IPPROTO_UDP" \
    $(find /nix/store -name parser.mono.c | head -1) | head -50
nix build .#checks.parity-gate                  # 22/22 ok
nix run .#flow-dissector-matrix-run -- \
    --testbed testbeds/hp2-hp5-x710.toml \
    --results perf-results/2026-05-Xx-hot-edge/
```

### Risks

1. **Priority table is workload-dependent.** Hardcoded constants are
   reasonable for general traffic but a real-traffic-tuned table
   would be different (e.g. QUIC-heavy networks have very high UDP
   dispatch frequency). Mitigation: ship the hardcoded table; later
   add a profile-guided variant if hard data justifies it.
2. **No measurable gain.** Possible — gcc may already emit jump
   tables that don't care about source order. Verify by inspecting
   the generated `switch` asm output before declaring success.

## Suggested execution order

R3.4 first (high leverage), then hot-edge (small clean win that
either lands quickly or proves a no-op).

  Week 1: R3.4.1 + R3.4.2 + R3.4.3 — hardcoded chain, verify, measure.
          Decision point: is the workload-dependent win compelling?
  Week 2: H1 + H2 + H3 — hot-edge ordering, verify, measure.
  Week 3: R3.4.4 + R3.4.5 — generalise R3.4 (only if R3.4.1-3 showed wins).

Each phase is its own commit + push + brief verification message.
Pause for review after R3.4.3's measurement (the workload-dependent
nature of the fast-path win means we may want to evaluate whether
the bigger generalisation work is justified).

## What this plan deliberately leaves out

- **R3.5 wider IR coverage extensions** beyond what R3.5.2 shipped.
  Doesn't move the headline (proven empirically); deferred until
  there's a BPF-target mono codegen where LTO doesn't apply.
- **R3.4 for the BPF target.** `c-bpf-xdp2` is verifier-rejected
  today; the fast-path emit is userspace-C only in this plan.
- **AVX-512 / SIMD field extraction** in the fast-path. Projected
  2 ns/pkt on Zen 4; not on our Zen 1 testbed.
- **Profile-guided optimisation** of hot-edge priorities. Hardcoded
  table is "good enough" as a starting point.
